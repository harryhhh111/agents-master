# agents-master 路线图

> 最近更新：2026-10-21。
>
> 本项目已从“驱动两个 Coding CLI 的传话工具”演进为用户自定义的通用个人 Agent。旧能力不是
> 被废弃，而是成为第一个持久子 Agent——“工作项目 Agent”的可复用执行能力；它不再定义整个
> 产品的入口与体验。

## 北极星

用户始终面对一个能长期相处的主 Agent：可以自然、无限地对话；理解事务在现实中持续变化；
在后台推进已托付的工作；从用户反馈中逐渐适应，但不擅自越过边界或把推断伪装成事实。

首批只覆盖人际关系、工作项目、长期目标。产品原则与已确认的初版交互见
[`product-discovery-v0.md`](product-discovery-v0.md)。

## 既有资产：工作项目 Agent 的执行能力

以下能力已完成并保留，是工作项目 Agent 的技术原型和可调用能力，而不是继续作为独立产品扩张：

- 独立 LLM 决策层、Ink TUI、Codex/Kimi 双 backend、session 增量读取、台账与轻量 memory；
- 在 `stock_data` 的真实传话闭环、回测和人工审批经验；
- 明确的硬边界：范围/优先级、方案、阶段推进、push、重大偏差和不确定性仍由用户拍板。

近期对这部分的修正仍可继续进行，但它们应服务于“工作项目 Agent 如何作为第一个子 Agent 与
主 Agent 协作”，而不是牵引通用个人 Agent 的产品定义。

## 阶段 0：产品关系与学习边界（持续校准）

目标不是补齐一份静态功能清单，而是确认主 Agent 如何在长期使用中形成可靠认识。

已确认：

- 初版为即时通讯式界面：主 Agent 一对一会话置顶；领域子 Agent 是可查看的群聊；提供独立的
  任务 Tab 查看任务与进展。
- 初版不做子 Agent 间直接对话或自动交接，主 Agent 是默认协调者。
- 系统从偏主动开始，并按用户反馈调整；例如周末社交安排可在周四适时提出。
- 事实带来源与时间。系统必须区分用户明确说明、合理推断与未知状态。
- 主 Agent 前台使用低延迟、非长推理模型，负责理解、澄清、轻量判断与协调；高思考强度的
  推理和执行移交后台任务或领域 Agent。
- 初版保持一条可持续追加、缓存友好的前台 context 主线。新用户输入立即进入持久化 inbox；
  普通后台进展不抢占对话，明确暂停、取消、纠正或优先级变更才优先打断。

本阶段尚未定案、但必须在实现前达成可体验的定义：

- **记忆的可体验落点**：已确定“原始证据 → 认识（Claim）→ 行为策略 → 当前上下文”的语义边界，
  仍需通过真实使用确定用户在何处查看来源、时效、访问边界与删除影响。
- **学习的边界**：哪些反馈可自动形成行为策略，哪些只能作为待确认认识；如何向用户解释一次建议
  依赖了什么认识，并允许其纠正、忘记或删除。
- **任务与对话的关系**：2026-10-20 已确认先识别行动意图，普通聊天不自动创建执行任务，
  明确委托也不必一律交给子 Agent；任务何时回来请求判断及具体呈现仍需通过使用验证，
  不以字段问卷打断自然交流。

这些问题应通过实际交谈与任务推进逐步确定，而不是事先为所有生活场景预设流程。

## 阶段 1：主 Agent 的最小真实闭环

验证一个能长期使用的最小入口，而非先构建多 Agent 平台：

1. 主 Agent 可持续对话，用户切换话题不会占住入口。
2. 它能识别并维护任务；任务 Tab 可呈现真实进展、待决与结果。
3. 它能把一个工作项目交给工作项目 Agent；后者调用既有双 CLI 协作能力在后台推进，并在恰当
   节点回来。
4. 它能从用户纠正中改变后续互动，并让这种变化可查看、可修正、可撤销。

验收标准是用户愿意把真实项目持续交给它，而不是功能列表齐全。

### 迭代尺度与下一步方向（2026-10-20 讨论确认）

这是个人专用项目，优先快速迭代。每轮先说明“用户能比上一轮多交给它哪件真实的事”，
用实际使用结果衡量进展；测试数量、内部模块完成度和发布设施不能代替真实能力交付。
长期个人 Agent 的完整愿景不应成为首个可用闭环的全部前置条件。

- 优先复用已有 CLI 执行能力及成熟开源实现；产品定义自主不意味着运行基础设施都要自建。
- 尽早运行真实部署与端到端任务，再按实际失败补足工程；保护凭据、数据与授权边界仍是必要要求。
- 优先交付范围有限、限制明确的能力；复杂恢复、更多执行器与领域扩展按真实使用需求推进。
  具体范围调整需明确记录，不能以快速迭代为由静默取消已确认的边界。

下一步方向是网页主 Agent 理解行动意图后，委派真实 Coding CLI 完成一个小任务，
期间用户仍能聊天，必要时回答追问，最终收到真实结果。普通聊天不应因此触发任务；
行为边界见 [产品发现稿](product-discovery-v0.md#从对话识别行动意图再决定是否委派2026-10-20-确认)。
具体执行器、测试仓库与授权范围尚待确定；单后台任务、单执行器、重启后人工恢复是讨论中提出的
简化选项，尚未作为已确认方案。本次讨论不代表真实 CLI 已接通或获准访问任意真实项目。

### 当前实现顺序：Dogfood Alpha

当前优先级不是继续补齐任务、记忆或多 Agent 平台，而是让用户能开始日用自己的主 Agent，
再让真实对话决定后续设计。现有任务/记忆控制面保留为可靠基础，但本阶段不扩展其用户功能。

1. **私有主聊天入口**：在现有 durable inbox + 快速前台 Runtime 之上提供最小 Web 聊天；
   只监听本机回环地址，展示持久历史，重启后恢复前台工作。它不是公网服务、任务 Tab 或工作台。
2. **显式主人上下文**：在私有数据目录维护用户可查看、编辑、重新加载的 `owner-context.md`。
   它是透明的起始背景，不等同于自动记忆；不得把个人内容写入 git 或预先做自动学习。
3. **使用证据与复盘**：将用户明确的“有帮助、打扰、不理解、记错”等反馈关联到对话，先形成
   可查看的产品证据；之后才提供显式的使用复盘和改进建议。建议不自动改变人格、代码或外部状态。
4. **由真实使用决定扩展**：反复出现且需要持续跟进的委托才进入任务；反复确认/纠正的信息才
   进入正式记忆；工作确实需要后台执行时才接入工作项目 Agent。子 Agent、任务 Tab 与自动委派
   都不是 Dogfood Alpha 的前置条件。

#### Dogfood Alpha Slice 1 状态：私有本地 Web 主聊天已完成

`agent main` / `npm run main:chat` 现已提供主 Agent 的持续终端入口：每条用户输入先进入
持久化 inbox，再由单一前台 drain 串行处理；在一次模型调用尚未完成时，后续输入仍可即时入库。
启动与显式 `/recover` 仅恢复 claimed `user-message`，普通 `timer` / `domain-update` 不会被前台
领取。调用失败不会自动重试，保留 claimed 状态并等待用户的明确恢复操作。

`agent main-web` / `npm run main:web` 现提供同一 Runtime 的私有本地浏览器入口：只监听
`127.0.0.1`，提供单用户密码登录和 30 天持久会话；首次设置密码需要启动终端的一次性初始化
凭据，之后直接访问固定地址，服务重启不再更换访问链接。页面显示耐久历史、排队/发送/回复状态、
错误与实时回复。远程使用通过 Tailscale Serve 私有 HTTPS 或 SSH 端口转发，不能配置公网监听；
未登录不能读取聊天 `/api/*` 或 SSE。首次 Web
启动在所选私有数据目录创建通用的 `owner-context.md`；用户
可查看并明确保存它，保存立即只影响未来前台回合。它是显式稳定背景，不是自动记忆、任务、Claim
或授权，个人内容不进入 git、日志或错误输出。详见 [私有 Web 主聊天说明](frontbrain.md#dogfood-alpha-slice-1私有本地-web-主聊天)。

该垂直切片尚不包含任务/记忆写入或工具调用、自动学习、反馈/复盘、自动委派、领域事件、任务 UI、
子 Agent、多 Agent 协作、外部动作或并行前台推理；它只验证持续自然对话的耐久入口。稳定前缀也
明确告知模型当前不能假装完成上述能力。

2026-09-16 旧探测输入仅 49 / 65 / 50 token，`cache hit=0` 是 prompt 太小、方法不足的观测，
不能推断没有缓存能力。探测现改为大段确定性合成前缀（目标实际输入 ≥512 token）、三次串行
预热（含分叉识别）、默认 2 秒有界等待及 continuation / common-prefix 两种测量；逐轮打印
真实 usage 和目标诊断。[方法与官方来源](frontbrain.md#不假定缓存行为)区分历史官方 64-token
存储单元说明与当前指南（不承诺固定 cutoff）。2026-09-17 的一次本机升级探测实际输入为
1074 / 1074 / 1076 / 1090 / 1075 token；首次预热 hit=0，随后重复、分叉、continuation 与
common-prefix 均报告 hit=896。它证明此调用形状能在预热后获得 provider 报告的共享前缀命中，
而非 provider 关于阈值、TTL、延迟或未来行为的保证。

初版不以“多主脑并行推理”为目标：前台对话和状态提交保持单一、可追溯的主线；后台任务可以
独立持续。若真实使用中快速前台仍频繁被长回合、打断或上下文切换拖慢，再以可取消的思考分支、
上下文版本和更复杂的注意力调度作为后续演进，而不是当前前置条件。

### Runtime 接线约束

- **当前模型别名与历史迁移**：`config.toml` 当前保留用户已批准的
  `model = "deepseek-flash"`；它是服务 API 中映射到既定 **DeepSeek V4.1 Flash** 的
  当前别名，并非模型选型变更。较早的决策、计划、回测等历史记录出现的
  `deepseek-v4-flash` 是该同一选型在当时使用的名称，应保留为历史证据，不应据此回退
  当前配置或改写历史文本。
- **存储路径归属**：SQLite store 只打开调用方提供的数据库文件，不创建其父目录。Runtime 的
  composition root 必须显式创建并校验数据目录、权限和备份边界，再实例化各 store；目录策略不能
  分散在持久化模型中。
- **规范时间戳**：所有持久化的 `*At` 字段使用 `Date.prototype.toISOString()` 产生的 UTC 时间戳，
  例如 `2026-09-15T12:34:56.789Z`。UI/CLI 和外部资料接入层负责将本地时区或自然语言时间转换为
  此格式；store 保持严格校验，不接受含糊的本地时间字符串。
- **SQLite 写入扩展验证**：当前单进程 Runtime 下的追加序号满足需求，且唯一约束防止静默损坏。
  若未来以多个进程/实例共享同一数据库，必须先做并发写入、锁等待和重试压测；只有实测暴露问题时
  才引入 sequence 表或其他跨实例序号方案，避免为 v0 预置不必要的复杂度。
