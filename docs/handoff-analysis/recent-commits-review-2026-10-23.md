## C1 / P1：清空按钮缺少 JSON 请求头，被稳定入口直接拒绝

引入提交：`416f032`。

位置：`src/main/coordination/web-page.ts:474`（本报告行号均按固定提交）；入口检查在 `scripts/main-web.ts:302`–`:306`。

`clearConversation()` 发送 `{method:'POST'}`，没有 Content-Type 和 JSON 请求体；入口要求所有写 API 使用 `application/json`。因此主聊和工作群按钮共用的请求路径都会返回 400，无法执行清空。

真实浏览器复现：登录 → 打开设置 → 点击“清空主 Agent 对话” → 接受确认。返回 400，提示“请求体必须是 JSON 对象”，合成历史仍在。对照请求补齐 JSON 头与 `{}` 后，同一路由返回 200。

最小修正：按既有控制/恢复接口的形式传 JSON 头与空对象；浏览器验收必须实际点击按钮，验证返回成功、当前历史消失和后续可继续聊天。已有路由测试自行补齐了请求头，所以没有覆盖产品按钮的真实请求。

## C2 / P2：信封剥壳误改用户原始 JSON

引入提交：`bfc9ef1`（展示）、`973f932`（模型上下文）。

位置：`src/main/coordination/model-host.ts:29`–`:33`；`src/main/coordination/web-page.ts:310`–`:314`，侧栏摘要同样无来源限制。

模型回复的格式兜底被无条件用于所有作者。用户发送的 `{"text":"SYNTHETIC_TEXT"}` 到模型时只剩 `SYNTHETIC_TEXT`；`{"author":"user","text":"SYNTHETIC_JSON"}` 也被变成字段值。页面同样执行这一转换，丢掉用户正在讨论的 JSON 结构。数据库原始用户消息未因此改写，但展示和模型输入已失真。

最小修正：保留用户输入原文，信封兼容处理限定到需要修复的 Agent 回复/历史，并收紧信封形状判定（当前仅有 text 字段也匹配）。补用户 JSON 在气泡、摘要、模型输入保持原样的回归用例。
