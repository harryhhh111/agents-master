# stock_data 手工传话实录分析 → v1 需求规格（2026-08-12）

> 数据源：本机 `~/.codex/sessions` 与 `~/.kimi-code/sessions` 中 stock_data 项目的会话记录。
> 提取方式：`extract.py` 剔除 think/tool_call/日志等中间过程，只留"用户消息 + agent 正式回复"
> （55MB → 1.4MB），产物在 `transcripts/`。
> 覆盖：Codex 侧 2 个大会话（07-22、07-28 起）+ Kimi 侧 7 个会话（07-14 → 08-12）。

## 1. 实际协作模式（与之前设想的对照）

**分工稳定但不是单边**：主流是 Codex 出 plan/runbook/review + Kimi 执行；但 Kimi 也频繁
评审 Codex 的文档（几乎每次都抓到 1-4 个实质问题），后期 Phase B/C 变成 Kimi 执行、
Codex 对抗性验收。**两边互为 plan/review 与 execute，随任务互换；不变的是"执行者
不自验，对方验收"。**

**验收闭环是核心循环**：交付报告 → 用户搬运 → 对方**独立核查**（不信报告数字，自己
查 git/DB、重跑测试）→ 通过或退回阻断清单 → 返工 → 再验收。每个任务平均 2-4 轮。
独立核查多次抓到实质问题（假测试计数、"已完成"实为未达标、UNEXPLAINED=1 报成 0、
未经方案授权的越权登记、BLD/BLDR 更名误判）。**双向互审是质量价值的核心来源。**

## 2. 传话的实际形态（对 v1 设想的重要修正）

**双向不对称**：

| 方向 | 载体 | 形态 |
|---|---|---|
| 执行方→评审方 | 聊天粘贴 | 结构化报告**整段原样粘贴**（结论、commit sha、测试数、表格、阻断清单、待决问题） |
| 评审方→执行方 | **repo 文档为主信道** | 方案落成 `docs/core/US_*_TASK.md`，消息只传"路径+3-6 行摘要"；review 意见则整段粘贴 |

**关键发现：用户几乎不做"选择性传递"。** review 意见要么整段搬要么不搬，不存在
"3 个 issue 只贴 1 个"。原因是**压缩已经在执行方侧完成**——用户传的是对方的结论性
报告，不是原始日志。v1 设想中"从 5000 行日志挑 3 个失败用例"的场景不存在于真实
传话链路中；真实需求是**按消息类型决定保真度**：

- review/验收清单：必须全文保真（每条都带实证，断一条就断链路）
- 任务文档：只传路径+摘要（共享文件系统即信道，对方自己读）
- 指针式传话随时间增多：只传 commit hash / 产物路径 / "看 git log"

**用户省掉的**：过程日志、diff、客套话、验证过程（怎么查的 EDGAR/怎么跑的 SQL）。
**用户加的**（每条贴文前的一句 framing，这是人的增值层）：

- 验收/裁判指令："你验收一下"、"你怎么看"、"这个辩解是否有道理"
- 优先级裁决："你先做前 3 项"、"#5→#6→#7"、"这个先往后放"
- 范围砍削："玩具项目，简化"、"不做企业级权限"
- 重点标注+指路上下文："特别是第 4 点的口径问题，不了解可以看最近几个 commit"
- 任务路由："你来收尾"（返工不一定给原作者）

**粘贴体与自写体风格差异明显**（结构化 markdown vs 口语短句），机器可据此区分
"转发内容"与"用户自己的裁决"。

## 3. 失控点 / 痛点（自动化的价值锚点）

1. **多轮验收循环的搬运疲劳**：07-24 用户原话"这么多时间和 token 花进去，有没有
   实际意义"。贴报告→验收→贴 blocker→再验收是最该自动化的循环。
2. **上下文回填**：用户手工把 Kimi 上一会话的输出贴回新会话（终端复制痕迹都在）。
   agent 直接读 wire.jsonl 即可消灭这个痛点。
3. **共享工作区并发**：任务文档被两边同时写冲突过；git 远端分叉（一边直接 push
   了 5 个提交）发生过。agent 需要感知"另一边正在改什么"。
4. **长任务失控**：4 小时全市场回填期间传话暂停，用户只能问"情况如何了"。
5. **治理漏洞**：执行方自批（approve by 自己）、双方共同滑向过度工程——需要
   纠偏通道，v1 阶段由人承担。
6. **进度追踪靠人肉**："哪版报告贴过了"靠重贴保证；文档状态靠用户催更。

## 4. v1 需求规格（从实录归纳）

**对话形态**：确认走形态 A（用户发起每轮）。实录中用户的不可替代角色是
**路由器 + 语义裁决者**，这部分保留给人；agent 取代的是**搬运工 + 核实员**。

**agent 的四个职责**（按价值排序）：

1. **可靠转发**：按消息类型保真——review/验收清单全文转，文档传路径+摘要，
   大 artifact 只传 `.ckflow/` 路径。消除复制粘贴。
2. **上下文自取**：直接读两个 CLI 的 session JSONL + git log，知道"另一边说了
   什么/改了什么"，不再需要用户回填和口头同步进度。
3. **传递前核实**：转发验收请求前先自己查（git diff / 测试 / 产物路径是否存在），
   把"报告声明 vs 实际状态"的初步核对做掉，过滤噪音轮次。
4. **状态追踪**：记录哪版报告已传、待决问题清单、谁在等谁，替代用户的重贴
   和催更。

**显式不做**（实录证明是人的核心价值区）：优先级裁决、范围砍削、push 批准、
"出方案"口令。agent 可以呈现待决项，但拍板权留给用户。

**消息分类schema（草案）**：`task_assignment` / `review_feedback`（全文保真）/
`completion_report`（结构化：sha+测试数+阻断+待决）/ `doc_pointer`（路径+摘要）/
`acceptance_request` / `user_decision`。分类决定转发策略，这正是"需要 LLM 而非
模板"的地方。
