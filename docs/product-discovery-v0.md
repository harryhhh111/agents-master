# 通用个人 Agent：产品发现稿 v0

> 状态：探索中。本文记录已经由用户确认的产品原则和首批待验证场景；它不是技术方案、
> 实现计划或功能承诺。
>
> 最近更新：2026-09-12。

## 1. 产品命题（已确认）

做一个由用户自己定义、长期存在的个人 Agent 系统。

- 用户始终从一个主 Agent 进入，并可以无限、自然地对话；主入口不应被任何长任务占住。
- 主 Agent 的主要价值是理解用户、持续维护上下文、判断和协调；重执行可由后台子 Agent
  完成。
- 对话不是任务的容器。用户委托的事务必须能独立持续、暂停、恢复、拆分、取消，并在用户
  转换话题后继续推进。
- 子 Agent 是内部实现手段，不是用户必须管理的一组 Bot。
- 产品自建、产品定义权在用户手中；OpenClaw、Hermes、Muse、Grok Bot 只作为体验和实现
  的参考，不作为产品替代或上游边界。

## 2. 当前范围（已确认）

首批只服务三个持续上下文：

1. **人际关系**：重要的人、承诺、互动脉络、合适的跟进时机。
2. **工作项目**：目标、协作、进展、阻塞、待决事项和交付。
3. **长期目标**：方向、现实进度、阶段性选择、调整与复盘。

当前明确不做：健康、家庭/居住、消费、旅行等其他生活领域。它们可在前三条主线跑顺后
再讨论，不能以“万能助手”为由提前膨胀范围。

## 3. 主 Agent 的角色与行为（已确认）

主 Agent 是**管家、伙伴与参谋的结合**：它应有自己的判断，也可以提出反对意见或替代建议，
但最终拍板权始终属于用户。

### 像人一样对话，而不是强行分类

通常，一句闲聊、一个委托、一个临时念头和一个长期承诺的区别对人是明显的，系统也应努力
自然理解。若它无法可靠判断，必须主动询问，不得用猜测代替理解。持续地“不懂就问”是它逐步
成为合格管家的必要习惯。

### 事实有时间，而非永久真值

系统记录的不是抽象的“用户体重是 65kg”，而是“用户在某日告知体重为 65kg”。它可以按常识
评估该事实至今仍大致适用的可能性，并在低风险对话中作为带时效的背景使用；涉及重要建议或
具体行动时，应说明它依据的是旧信息并向用户确认。系统必须区分：已知事实、合理推断、未知
状态，不能将推断伪装为当前事实。

### 证据、认识、策略与当前上下文

系统不应把一段长摘要或模型上下文当作全部记忆。原始资料、从资料得到的认识和 Agent 的
行动方式是不同层次；这是对人类经历、知识、习惯与工作记忆的借鉴，不是对生物机制的照搬。

1. **原始证据**：聊天、任务事件、文件、网页和外部资料的原始记录，带时间、来源和访问边界。
   它是可追溯的依据，不因被收录就自动成为“知识”。
2. **认识（Claim）**：有证据支撑、可版本化的陈述，记录其范围、时间、确定程度和来源。个人
   记忆与外部知识不是两套重复存储，而是认识的不同范围：前者关于用户、人际关系、项目和目标；
   后者关于外部世界或项目资料。例如“用户目前旅居昆明”与“本项目采用 TypeScript”都是认识，
   但可指向不同的原始证据。
3. **行为策略**：条件到 Agent 行为的规则，而非关于世界的陈述；记录触发条件、行为、依据、
   适用范围、时效和确定程度。例如“适合在周四提出周末安排，近期已讨论则不重复”。
4. **当前上下文**：为这轮对话或当前任务临时编排的少量证据、认识与策略；它可在任务结束后缩减，
   不等同于长期记忆。

任务是独立的运行状态，不属于上述记忆层。新的经历先进入原始证据；系统在需要时从证据形成或
更新认识，并只在它确实需要改变后续行为时形成策略。用户明确说“我偏好在周四考虑周末安排”是
一条个人认识；“Agent 应在周四适时提起”才是一条行为策略。它们可以关联，但不必重复创建。

用户明确说明的内容、系统的合理推断与未知状态始终分开标注。外部资料本身保留在原始证据中；
由其支持、可检索和可时效判断的结论才构成知识性认识。

该模型是针对本产品的综合语义：借鉴事件溯源、数据溯源、知识图谱和持久 Agent 的成熟思想，
但不绑定任何框架、图数据库或记忆产品；具体存储与检索实现必须服从本产品的可追溯、可纠正、
可忘记与访问边界。

### 访问边界，而非含糊的“权限”

这是单用户系统；这里的访问边界不是多用户权限管理，而是规定哪些内部角色可以为哪件事读取、
检索和使用信息。原始证据与认识应能标明：主 Agent 只能见摘要还是可见原文、哪个领域 Agent
可以检索、以及是否可进入当前任务上下文。对外披露默认不允许；代表用户采取外部行动的授权是
独立规则，不能混入记忆访问边界。

### 纠正、忘记与删除

- **纠正**不篡改历史：旧认识保留其来源和适用期间，新认识从新的时间点生效；冲突无法可靠
  判断时，系统应询问。
- **忘记**是撤销一条认识或策略的检索和使用资格。原始聊天可仍由用户保存，但不得因为系统
  以后重新读取旧聊天而再次自动使用这条信息；只依赖被忘记认识的策略也应失效。
- **删除记录**进一步删除原始证据及其索引。执行前系统必须展示受影响的认识、策略和活跃任务；
  仅以该证据为依据的派生项默认一并撤销，而有独立证据支持的项可以保留。系统不得把失去依据的
  认识静默降级为推断；用户若希望保留，需明确重新确认。

记忆的“可见”不等于把所有内容常驻界面。系统在据记忆提出建议时，应能说明依据；用户也应
能在相关主会话、领域会话和任务中查看“它目前知道什么”，并直接用自然语言纠正或遗忘。

### 主动性从偏主动开始，再由关系校准

初始人格可偏主动，主动指出值得关注、可能被遗忘或可更好处理的事情。用户若觉得被打扰，
可直接表达；系统应把这类反馈吸收为后续互动偏好。主动与克制不是一次性配置，而是双方在
长期沟通中共同校准的关系。

### 多事务响应与呈现形态

多件事同时进行时该如何回应、何时展示什么，仍是主 Agent 的核心问题；但初版呈现已收敛为
熟悉的即时通讯形态，而不是提前构建自由布局工作台。聊天记录不是人与管家关系的最终呈现，
但它是当前最合适的起点。

- **聊天 Tab**：类似微信或 Telegram。用户与主 Agent 的一对一会话始终置顶，是唯一默认入口。
  每个长存领域子 Agent 对应一个可进入的群聊，群内包含用户、主 Agent 与该领域 Agent；主 Agent
  的委派、领域 Agent 的追问与结论可被用户审阅。
- **任务 Tab**：类似游戏任务列表，集中显示所有任务；进入任务后可查看目标、当前进展、事件、
  证据、等待用户决定的事项及完成/暂停状态。它是跨会话的承诺清单，不是复杂工作台的替代品。
- **未来而非初版**：可自由布局的工作台仍是值得探索的方向，但要等聊天与任务两种基本关系被
  验证后再决定其必要性。

### 子 Agent 的协作边界（初版）

初版不实现子 Agent 之间的直接对话或自动交接。默认链路为“用户 ↔ 主 Agent ↔ 领域子 Agent”；
主 Agent 负责判断信息是否需要跨领域传递，并将相关结论带入相应会话或任务。这样可避免内部
对话膨胀、重复执行和责任不清，也使用户始终能理解谁在为何事工作。未来如有必要，可在明确的
任务目标和可见交接前提下，再增加临时跨 Agent 协作。

## 4. 不可妥协的体验原则（已确认）

### 入口永远可用

用户可以在后台工作进行时随时提问、换话题、补充事实、改变优先级或要求停止。用户的新指令
优先于后台工作；已发生的外部动作另行如实呈现，不能假装能撤回。

### 事务持续，但不骚扰

系统应该在状态变化、风险、交付或真正需要用户判断时回来，而不是用频繁的进度消息占据
注意力。用户可定义希望被打扰的程度。

### 记忆可见、可纠正、可忘记

系统对人、项目、目标和偏好的长期认识必须能追溯来源，并允许用户查看、纠正、删除或要求
遗忘；不能把关键判断藏在不可见的聊天摘要中。

### 外部后果必须有边界

系统可先阅读、整理、起草、建议和准备；未经明确授权不得代表用户联络他人、作出承诺、
发布内容、消费、删除或改变外部系统。授权应针对具体动作及范围，而不是一句泛化的聊天许可。

## 5. 首批场景假设（待用真实生活校准）

这些不是已决定的功能，而是用来观察用户是否愿意长期托付的最小故事。每条都必须验证：
系统知道什么、后台做什么、何时打扰、什么必须停下询问。

### A. 人际关系：承诺的可靠守护

用户随口说：“我答应周末帮朋友看一份东西。”

- 系统识别这不是即时问答，而是一项对人的承诺；记录对象、事情、时间线和不确定处。
- 到合适时间先向用户确认这项承诺是否仍有效、是否已完成；不直接替用户联系朋友。
- 用户更新事实后，系统更新该关系上下文，避免以后重复提醒或忘记。

**待验证点**：什么才是“合适时间”；怎样提醒才像可靠的助手而非待办软件。

### B. 工作项目：用户不再充当信息搬运工

用户说：“这个项目这周要推进。”

- 主 Agent 将其维持为独立工作流，整理目标、当前事实、协作方、阻塞和待决项。
- 它可以让后台 Agent 调研、执行或核验，并保留原始证据与交接记录。
- 用户中途讨论无关话题时，主入口立刻响应，项目仍在后台推进。
- 主 Agent 仅在优先级冲突、范围变更、外部动作、风险或交付点请求用户判断。

**待验证点**：用户是否能在不反复追问的前提下掌握真实状态，并确信系统没有自作主张。

### C. 长期目标：适应现实而非机械催促

用户说：“我希望在半年内完成一个重要方向。”

- 系统先理解目标为何重要、有哪些约束和模糊处，而不立即生成僵硬的每日计划。
- 它把工作项目、承诺和时间变化作为现实信号，持续判断目标是否在推进、漂移或已不再适合。
- 它在需要选择、复盘或调整时提出有依据的建议；用户可暂停、修改或结束目标。

**待验证点**：系统如何做到有帮助但不说教；什么证据足以支持“该调整目标”的建议。

## 6. 下一轮产品发现（尚未开始）

按场景逐条收集真实交互，而非先设计架构。每个案例都应记录从交代事务到完成/暂停的时间线，
以及每个“系统可自行做 / 必须汇报 / 必须先问”的节点；但收集不是目的，必须能支持后续产品判断。

### 证据驱动的发现闭环

每个待验证点预先约定三类内容：支持假设的证据信号、反向信号，以及信号出现后可能作出的
“保持 / 调整 / 收缩场景”决定。用户的明确反馈权重最高；行为数据只是线索，不能脱离当时情境
单独下结论。例如，频繁查看任务可能代表不信任，也可能只是新鲜感；暂停长期目标不必然代表
系统在说教。

| 场景 | 要验证什么 | 支持信号 | 反向信号 | 可能的产品决定 |
|---|---|---|---|---|
| 人际关系 | 周四主动提出周末安排是否合适 | 用户据此安排、自然继续讨论或主动补充社交计划 | 明说太早/太晚/不想被提醒；多次忽略后仍感到打扰 | 调整时机或频率；改为只在相关对话中建议；收缩主动范围 |
| 工作项目 | 用户是否确信系统不会自作主张 | 用户持续托付任务、审批边界清晰、能在不反复追问下理解状态 | “谁让你这样做”“为什么没先问我”等纠正；意外越权或任务状态难以理解 | 收紧授权；改善任务详情和依据呈现；调整主 Agent 的汇报方式 |
| 长期目标 | 建议是否有帮助而非说教 | 用户主动要求继续复盘、采纳建议或给出有内容的反驳 | 要求停止提醒、回避讨论、明确评价为有压力或空泛 | 降低主动性；改为用户发起；收缩或替换该场景 |

一次验证不以凑够固定数量的案例为完成条件。只有在不同的真实情境中已出现可判读的信号，
系统据此作出明确调整，并且该调整至少又经一次现实使用检验，才可将某项结论暂定为有效。若
持续没有可判读信号，或反向信号表明场景本身不值得托付，应收缩、替换或暂停该场景，而不是
继续累积无结论的观察笔记。

## 7. 参考产品的边界

- Muse：借鉴长期后台工作、上下文随现实变化而调整、敏感动作单独审批的体验。
- Grok Bot：借鉴持久角色、可见交接、从一次成功任务沉淀为 routine 的方式。
- OpenClaw / Hermes：借鉴自托管 gateway、记忆、技能、后台任务和多 Agent 的实现经验。

不应照搬：任何上游项目对 workspace、Bot roster、配置文件或渠道路由的产品中心性。它们是
实现候选，不应反向定义本产品的用户体验。
