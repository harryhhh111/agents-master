# Agent 系统第一轮实现方案（评审收敛稿）

日期：2026-10-15。状态：**评审后的设计基线；接入能力及实施参数待验证，不代表已授权上线**。

本轮只产出方案，不修改应用、部署或执行权限。已有产品决定见
[产品发现稿](product-discovery-v0.md)，源码参考见
[OpenMausBot / Rakazo 调研](open-agent-reference-study-2026-10-15.md)。
本次吸收 Kimi 评审及后续讨论，收敛设计方向并修正代码事实。设计基线仍可由用户调整；
字段和模块名用于表达边界，不要求按字面实现。具体项目、可传输数据和 backend 的选择
不能由这份文档替用户批准。

## 0. 本次评审形成的结论

| 事项 | 本轮设计基线 | 不能据此推导 |
| --- | --- | --- |
| 领域判断 | 适配已有 AgentCore，CLI 是可替换执行能力 | 缺一套 harness，需要从零重写；多一个模型就更安全 |
| 日常入口 | 群聊可写，默认路由领域 Agent；明确且在既定范围内的只读委托不重复确认 | 任意群消息都可触发执行；含糊指令也自动开工 |
| 结果交付 | 结果主动回主入口，安全点简短汇报，普通进展留群聊；不被连续输入永久饿死 | 改写进行中的 context，或每条进展都打断用户 |
| 执行范围 | 筛选项目快照，先接一个通过验证的 backend | 快照本身是沙箱；已确定哪个 backend 满足权限要求 |
| 回传机制 | 独立持久 outbox，经统一前台调度消费 | 新建第二个主脑循环；复用遗留 domain-update 的恢复语义 |
| 触发来源 | 呈现消息与执行事件分开，来源由可信入口绑定 | 仅按消息文本、作者昵称或模型声称的 origin 授权 |
| 先后顺序 | 工具协议与执行权限先做小型预检，再推进迁移及完整接线 | 本轮已经跑过这些预检，或已授权访问任意真实项目 |

以下选择不再保持等权备选；若预检暴露阻碍，再带证据讨论调整，不静默降低边界。

## 1. 这轮要交付什么

用户在现有主聊天委托一次指定项目检查。主 Agent 理解请求并交给长期存在的工作项目
Agent；派工和结果在对应群聊里可查看。后台工作时主聊天仍可继续，遇到问题能回来询问，
完成后能回报实际发现。刷新、重启或失败不会让系统假装事情从未发生。

第一轮以只读项目检查作为设计目标，不是把产品永久限制成项目审查工具。
自动建任意 Agent、子 Agent 互聊、自动记忆学习、云桌面、完整任务 Tab 不作为本轮前置条件。

**已经确认，不重新讨论：**

- 主 Agent 是默认入口，负责理解、判断、澄清与协调，用户保留最终决策权。
- 前台短回合保持单一提交主线，长工作移至后台；不追求同一会话多个主脑同时提交。
- 每个持久领域 Agent 对应用户、主 Agent、领域 Agent 三方群聊；委派应在群内可见。
- 初版不做领域子 Agent 之间直接通信；CLI 是工作项目 Agent 的能力，不是产品身份。
- 原始证据、Claim、Policy 和当前上下文的含义不因引入子 Agent 而改变。

**本稿明确的三条边界：**

1. 谁长期存在、谁负责判断，哪些上下文属于谁。
2. 怎样从对话变成真实委派，怎样等待、追问、回传和恢复。
3. 怎样限定可读、可执行、可传出的范围，并实际验收。

## 2. 边界一：身份、职责与上下文

### 2.1 三层角色，不等于必须新增三套模型循环

| 层 | 职责 | 不应承担 |
| --- | --- | --- |
| 主 Agent | 理解用户、澄清意图、确定领域、表达判断、发起有边界的委派、接收摘要 | 吞入所有项目日志；同步等 CLI 跑完；擅自批准新的外部行动 |
| 工作项目 Agent | 维护项目背景、理解具体工作、组织执行与检查、整理证据、提出问题 | 把 CLI 自述直接变成已验证事实；跨领域读取无关个人信息 |
| CLI 执行器 | 在批准的工作区与能力范围内阅读、分析，按要求返回产物 | 自己成为长期产品身份；决定扩大授权或静默切换其他项目 |

领域 Agent 需要真正的领域判断，不能只有一个固定转发 prompt 和昵称。
但它的“脑”不必先自建一套通用工具执行 harness。

**本轮采用的设计方向：**借用现有 AgentCore 的决策/传话能力，抽出受限的工作项目适配层；
把领域会话、运行状态、请示和产物接入持久协调层。CLI 的内部推理、工具循环、
原生 session 管理由原 CLI 负责。不能原样把现在的 AgentCore 放到 Web 后面：
它仍有进程内 messages/RunRegistry、旧工具集、默认仓库内 memory/state 等假设。

AgentCore 已有 OpenAI 风格工具循环、11 个工具、回合串行化和后台完成通知；
缺口不是“没有 harness”，而是把这些能力从单进程工具提升为持久的领域运行时：

1. 将内存 messages 改为冻结锚点、版本化项目摘要和可恢复协议记录驱动的上下文。
2. 按首轮能力收窄工具面，禁用不在范围内的工具，而非把旧 11 个工具全部开放。
3. 将 askUser 的内存 Promise 改为持久 question 与后续回合恢复。
4. 将 Run 真相落到 SQLite；后台完成去重不能依赖 prompt 提醒模型“已处理则忽略”。

不采用“单个 CLI 同时就是领域脑”的薄方案作为首轮基线。理由是领域身份、项目理解和
协作策略应独立于某个执行器，而不是 AgentCore 天然更安全。主 Agent、领域 Agent 和 CLI
都可能误判；权限由宿主及执行环境强制，可信结论由证据支持，两个模型认可不等于独立验证。
复用已有循环，不意味着完整搬迁旧 TUI，也不意味着另造通用 CLI harness。

### 2.2 一个工作领域 Agent，不默认一个项目一个 Agent

建议初版只有一个持久“工作项目 Agent”，先绑定一个用户明确选定的项目。
以后可以管理多个项目，分别拥有 projectKey、项目背景和执行会话；不要因为一次新委托
就创建一个新的 Agent。首轮不实现多项目调度，但数据必须保留项目维度，禁止串上下文。

身份与执行标识分开：

| 标识 | 生命周期与作用 |
| --- | --- |
| agentId | 长期领域身份；改名、进程退出、换执行器不改变它 |
| conversationId | 主私聊或领域群聊；承载消息、参与者和可见范围 |
| projectKey | 用户选定的项目绑定；服务端解析为允许的工作区，不由模型指定任意路径 |
| assignmentId | 用户一次明确委托；包括原意、范围、来源、状态和返回位置 |
| runId | 完成委托的一次执行尝试；重试产生新 run，保留旧证据 |
| executorSessionId | 某执行器原生 session 的引用；只在同执行器、项目、权限范围内续接 |

一个 assignment 可包含多个顺序执行/审查 run。Codex 的 session 不能交给 Claude 续接；
切换执行器时创建新 session，从受控上下文恢复，并标明未继承原生历史。
若使用独立审查者，其 session 还应按执行角色隔离；不能把同一个分析 session 改名为
“独立验收”，也不能让审查者无条件相信前一个执行器的自述。

### 2.3 上下文归属和实际加载

| 信息 | 持久归属 | 主 Agent 默认收到 | 工作项目 Agent / CLI 收到 |
| --- | --- | --- | --- |
| 主对话与全局主人背景 | 主会话/现有私有背景存储 | 相关背景及主线历史 | 不自动全量转发；只给完成委托必要的约束 |
| 领域身份与职责 | Agent 记录 | 简短目录：有谁、负责什么 | 本领域职责与明确权限限制 |
| 项目背景与用户确认的决定 | 项目上下文，附消息/文件来源 | 当前事项的简短摘要，必要时再查 | 本项目摘要、相关证据、近期领域消息 |
| 群聊 | 领域 conversation | 派工/追问/结果事件及按需读取 | 按序、有界地读取本项目相关消息 |
| CLI 工具轨迹、stdout/stderr | 私有执行产物目录 | 不直接注入 | 只加载经过选择和过滤的必要产物；不加载隐藏思考 |
| 结论与未解决问题 | 委派结果及领域群聊 | 摘要、状态、证据引用、需用户决定处 | 本次产物与后续跟进上下文 |

“属于子 Agent”不等于主 Agent 永远看不到；主 Agent 可以为具体协调事项按权限读取详情，
但不将全部详情永久塞进主线。群聊里的参与者身份不等于每条消息都要唤醒所有模型。

建议每轮组装：稳定职责/协议 → 版本化项目摘要 → 截至本轮锚点的必要消息 → 当前委托。
原生 CLI session 在同一项目下尽量续接；领域身份不依赖这个 session 永远有效。
上下文接近预算时生成带来源游标的工作摘要，保留原始记录；摘要失败或有缺口时
报告上下文不足，不静默截掉关键约束继续执行。具体字数/token 上限通过接入测量确定。

首轮项目摘要属于可追溯的工作检查点，不是新增一套自动 Claim/Policy 学习系统。
事实、用户决定、模型推断、待确认项分栏保存。旧摘要和 CLI 历史都不能覆盖新的明确纠正。
若不能可靠刷新旧原生 session 中的约束，应重建 session，不为缓存牺牲正确性。

### 2.4 群聊是不是只读的？

**本轮默认群聊可写。**用户可以查看群聊，也可以直接补充信息、回答问题或纠正范围。
初版采用明确路由：普通领域消息默认给工作项目 Agent，@主 Agent 才交主 Agent；
领域结果通过关联回执向主入口汇报，不让三个角色自动你一句我一句。

从主聊天转来的委托只形成一次派工；群聊可见消息是同一委派记录的呈现，不能再次触发执行。
用户直接在群里布置新工作也走同一个授权/派工入口，不能绕过校验。

数据层约束：保存 Message 不自动创建可执行事件。用户输入须来自已鉴权的提交入口；
派工触发须来自通过验证的委派事务；结果触发须来自宿主记录的回执。
作者、来源类别、关联 assignment/run 和幂等标识由服务端绑定，不由模型或浏览器任意指定。
群聊中的派工摘要、工具结果和回传回显只是呈现，不能再被扫描成新用户输入。

## 3. 边界二：委派、等待和回传

### 3.1 什么话会变成工作

“帮我检查已经绑定的项目”是明确委托；“以后可以检查一下”不自动开工。
“这个项目”无法唯一解析时先问，不用模型猜绝对路径。

建议主 Agent 只拥有少量领域工具：查询领域/项目、提交委派、查看状态、回答待决问题、
请求取消。没有任意 shell、任意路径和任意 Agent 创建能力。

一次结构化委派的概念输入：

```ts
type DelegateWork = {
  targetAgentId: string;
  projectKey: string;
  objective: string;
  scope: string[];
  completionCriteria: string[];
  contextRefs: string[];
};
```

用户来源消息、会话身份、授权范围、幂等键由可信服务端绑定，不能相信模型传入的
“已经批准”“来自用户”或“权限足够”。自然语言意图判断仍可能出错：服务端只能
强制执行具体能力上限，不能声称 schema 校验证明了用户真实意图。

已绑定项目、已批准数据及只读能力范围内的明确委托直接接收，不为同一件事重复问一次“是否确认”；
不清楚意图/范围时询问。首次项目绑定和模型服务的数据边界需由用户明确选定。

模型工具协议需要先用当前配置实测；当前 FrontBrain 只有文本 completion，
但 AgentCore 已经通过配置的客户端传递 tools。FrontBrain 类型没有 tools 字段只能证明
前台尚未接线，不能证明当前模型不支持 function calling；旧循环存在也不能替代当前组合的实测。
若 provider 不支持所需工具协议，应显式报不可用或另行讨论受校验的结构化输出方案，
不能退回从普通聊天文字中匹配“开始执行”。

### 3.2 最小完整时序

```text
用户 → 主聊天 inbox（先保存，立即确认消息收到）
           ↓ 主 Agent 短回合理解/澄清/提交委派
       事务：委派 + 群聊派工消息 + 派工回执 + 待调度记录
           ├→ 主聊天展示“已交给工作项目 Agent”，前台回合结束
           └→ 后台领域调度 → 工作项目判断 → 受限 CLI run
                                              ↓
                       事务：结果/问题/失败 + 群聊消息 + 回传 outbox
                                              ↓
                       主入口安全回合消费 → 汇报/询问 + 消费确认
```

前台只等待本地接收事务，不 await CLI 结果。“已收到消息”“委派已接收”
“执行已开始”“检查已完成”必须是不同的真实状态。
派工失败时不展示成功派工文案；模型在工具结果前说“我安排了”不构成系统确认。
建议已接收回执用持久消息卡直接呈现，即使后续模型措辞失败，用户仍能看到真实状态。

模型调用和 SQLite 事务之间不持有长锁。工具决定一经验证即持久化；恢复时先读已提交
决定，不能重跑模型后生成新参数再创建一份委托。首轮建议每条用户输入最多接收一个
委派，幂等槽位绑定源事件；如需拆多个任务由下一次明确协议扩展。
用户重试同一消息 ID 不重复派工；用户稍后主动再次发送相同文字是新消息，不能按文字
去重吞掉真实新委托。

工具请求/响应应有独立的持久协议记录，包含调用 ID、参数、执行回执与源回合；
群聊可见派工摘要不能替代这份记录。模型续接必须保持 tool call 与 tool result 的合法顺序，
不能把后台结果插在尚未配对的工具消息中。重试已提交工具应返回原回执，而不是再次执行。
前台每轮的调用次数与总耗时必须有界；提交委派后结束该轮，不在前台轮询结果。

回传采用独立 outbox 表，不复用遗留 domain-update/timer。本轮继续让这两类遗留事件
不被新消费者领取或恢复；当前 runtime 已经通过专用 user-message 领取和恢复规避了误领，
这是一条需要保留的约束，而非待修复的现存误领 bug。
outbox 负责耐久投递与去重，不直接启动另一个前台模型循环。统一前台调度在安全点领取回执，
冻结上下文后生成汇报；汇报消息与 delivered 标记在同一事务提交，重复投递返回已有结果。
delivered 表示汇报已持久进入目标会话，不表示 SSE 已到达浏览器，更不表示用户已读。
浏览器断线/关闭时照常完成持久交付，重连通过历史和消息 ID 恢复，不依赖一次网络通知。

### 3.3 并发及新的用户输入

建议初版前台一条短回合队列，工作项目 Agent 一条独立后台队列。
同项目原生 session 不允许两个 run 同时写入。第二个工作委托如实排队，不阻止主聊天。
领域 Agent 等用户补充时，不占用一个活跃 CLI 进程；其他独立委托可继续，顺序关系需保留。

普通后台进展写群聊和状态，不每步唤醒主 Agent。完成、失败、需要输入各形成有类型的回传。
每次模型请求使用冻结的 context 与消息锚点；中途新消息/结果留给下一回合。

结果交付分为三层：终态立即持久保存；群聊及主入口关联的结果提示可恢复地更新；
主 Agent 在安全回合主动简短汇报。前两层不等模型措辞，也不依赖网页是否打开。

明确停止/取消控制优先。用户输入通常优先于普通汇报，但采用有界公平调度：
每个安全点检查待回传结果，达到连续用户回合数或等待阈值后安排一次汇报，不能被不断到来的
消息永久推迟。相关结果可以合并，但保留每项独立身份和消费确认；先核对取消/纠正后的版本。
阈值在调度规格中定义并测试，它不是模型或网络故障时的墙钟交付保证。
需要用户回答的事项明确展示，模型转述失败不隐藏原问题；普通进展不逐条触发汇报。

默认主动交付不等于无条件打断：不改写在途 context，不插入未配对的工具消息，不重复刷屏。
此默认可按用户反馈调整，不能用“结果一定不打扰”替代长期互动中的判断。

用户说“停一下”但无法确定目标时先问；可提供关联 run 的停止按钮作为确定性快速路径。
自然语言取消仍需要短回合理解，不承诺零延迟。取消与启动的竞争由服务端版本检查解决，
不能只改 UI。补充消息属于同一委托还是新任务不明显时，同样询问。

### 3.4 状态不把执行成功、结论和交付混在一起

| 对象 | 建议状态/含义 |
| --- | --- |
| Assignment | queued、running、waiting_input、cancel_requested、completed、failed、cancelled、interrupted |
| Run | starting、running、succeeded、failed、cancel_requested、cancelled、unknown |
| 回传 | pending、processing、delivered；失败可再投，不回滚已有工作结果 |

CLI exitCode=0 只能证明进程正常结束。工作项目 Agent 还需检查是否回答了目标、
证据是否存在、有哪些未验证项。完成“检查”并发现问题是成功交付检查，不等于项目无问题。
主 Agent 可以质疑报告，但不能声称自己独立执行过那些命令。

结果建议包含 summary、findings、evidenceRefs、limitations、question（如需输入）。
原始产物与简短报告分开；模型自述与宿主记录的退出码、时间、文件引用分开。

waiting_input 记录 questionId、问题、assignment/version 和允许的回答范围。
主聊天或群聊的回答都关联同一个 question；从一个位置回答后，另一个位置显示已答。
回答过期问题或在委托已取消后回答，不自动复活工作。
“需要你批准修改文件”不因为用户回答普通问题就变成写授权；本轮直接说明暂不支持执行修改。
旧 AgentCore 的 askUser 回调不能只包一个跨小时等待的 Promise：应持久写入问题、结束
当前领域回合，在回答事件到来后从记录恢复。CLI 不支持可恢复提问时，结束本次 run，
保存已完成部分，收到答案后创建后续 run，不假装原进程一直在等。

### 3.5 取消、故障与重启：承诺什么，不承诺什么

- 取消先记录请求，再停止对应子进程树；确认停止后才显示 cancelled。无法确认则报告
  中断/状态未知，不能声称已经停干净。停止不等于撤销已经发生的效果。
- 回执附 assignment 版本与 run 标识；取消/纠正后旧结果仍可作证据保留，但不得覆盖新状态，
  不得以“最新成功”展示，也不得继续执行旧授权。
- 服务重启后，queued 可重新领取；终态未回传可补投；waiting_input 继续等原问题。
- starting/running 不自动重新执行：可能已经启动或做过事，但来不及写完成记录。
  先核对宿主执行标识、原生 session 和终态产物；证据不足标 interrupted/unknown，等待用户选择。
- 进程 PID 不是身份，PID 存在/不存在都不能单独证明原 run 正在运行或已经完成。
  systemd 停机策略、子进程组和新进程接管须实际测试，防止孤儿执行与重复启动。
- 同一进程内一次领取防并发重复；持久幂等防重复接收/回传。不承诺任意崩溃下
  外部进程或外部副作用 exactly-once。安全默认是状态不明时不重跑。
- 一个后台结果的转述失败不应堵住用户聊天；保留待回传状态和群聊结果，允许有界重试。
  前台自身 API 失败仍如实显示原有恢复入口，不把失败伪装成后台忙。

## 4. 边界三：授权、数据和“只读”

### 4.1 只读不是一句 prompt

现有 CodexBackend 有 sandboxMode 配置，默认 workspace-write；ClaudeBackend 有
permissionMode 配置，默认 acceptEdits。这是已有可复用入口，不等于它们已经满足本轮隔离要求。
KimiBackend 没有显式、受校验的隔离配置；不能据此断言 Kimi CLI 自身没有权限机制。
AgentBackend 尚无统一能力声明。runCommand 合并全部宿主环境变量，默认产物目录在 cwd 内，
AgentCore 默认使用仓库内 state/memory；不能直接拿这些旧行为证明新入口是最小权限。

必须分别验证文件写保护、敏感文件可读范围、工具网络出口和凭据继承。
全量环境继承构成秘密隔离/最小权限风险，但不单独证明文件写保护失效；反过来，
文件完全只读也不能防止越界读取和数据外传。

建议第一轮的允许范围：读取用户指定项目的已批准内容，分析文件/差异，写入系统自己的
私有会话和产物目录。禁止改项目、git commit/push、安装依赖、运行仓库脚本、任意网络访问、
修改服务、使用 root 权限。测试命令不天然只读；要运行项目代码必须另行明确范围。
开发者实现本产品时运行测试，与用户产品入口中的“只读检查”是两套不同授权。

### 4.2 检查什么版本、什么数据

首轮基线选用筛选后的只读项目快照；实时视图仅保留为后续可讨论的替代方向：

- **首轮：筛选后的只读项目快照。**记录基准 commit、包含的工作树改动和文件清单/摘要；
  排除凭据、私有数据、无关产物，不跟随越界符号链接。优点是输入稳定、可复现；缺点是
  不是实时工作目录，未包含的未跟踪文件必须告知，不能假装审查了全部内容。
- **备选：真实工作区的受限只读视图。**无需复制，但必须验证敏感路径不可读、工具不能
  越界、并发编辑能被检测。仅传 cwd 或设置 CLI read-only 不能证明这些条件全部成立。

快照也不是完整安全隔离：它仍需运行时文件访问和网络边界，不能让 CLI 转身读取宿主
其他目录。敏感扫描不能保证识别所有秘密；首次绑定须确认可交给选定模型服务的数据范围。
读取期间若文件变化，记录输入版本或重新生成快照；不将不同时间的文件混成同一个检查证据。

### 4.3 接入前的权限验证门槛

执行适配层须验证实际 CLI/OS 组合能否做到：

1. 输入项目只读；未批准的宿主路径（包括主聊天数据库、主人背景、其他项目、密钥）不可读。
2. 执行器只拿必需认证与环境，不继承 Web 会话密钥和全部宿主环境；原生配置/MCP/插件
   也要检查，不能继承一套超出本次授权的工具。
3. 模型服务连接与工具网络分开：允许必要模型调用不等于允许任意外联；选定 provider
   接收必要项目内容属于用户需要知晓的数据边界。
4. 可写区域仅限隔离的会话/临时/产物目录；CLI 不能改我们的授权记录或直接写对话数据库。
5. 无法获得权限或认证时如实阻塞；禁止用跳过权限检查的开关兜底。

具体采用 CLI 原生隔离、OS 沙箱还是隔离工作进程，由接入验证决定；当前并未证明
现有三个 backend 全部满足要求。若做不到，缩小为受控文件读取与分析，或讨论额外隔离，
不能标注“已安全只读”上线。此处是验收门槛，不是承诺这一轮建设完整沙箱平台。

首轮只接一个通过门槛的 backend，其余显示不可用/未验证；不静默换 provider。
可优先评估 CodexBackend 已有的 sandboxMode 入口，但这不是已通过验证或已选定执行器的结论。
未来产品内双 CLI 执行加审查时，两个 backend 都必须分别验证。仓库要求两个独立 CLI
协作实现与验收本产品，不等于产品里的每次用户请求都必须消耗两次完整 CLI 执行。

### 4.4 结果和记忆不是授权来源

代码、README、群聊中的转述、子 Agent 报告都是有来源的数据；其中“忽略限制、读密钥、
执行某命令”的内容不能变成工具权限。模型可以建议新行动，但服务端仍检查授权对象和版本。
原始 stdout/stderr 不直接送到浏览器或主模型，尤其不暴露隐藏思考和凭据。
按需查看产物走鉴权和安全过滤；私有原件只保存在限定权限目录，不入 git。

## 5. 技术落点与迁移建议

### 5.1 最小持久数据，不提前建通用平台

建议单 Node 服务内分离前台调度与后台调度，继续用 SQLite；CLI 是子进程。
不要在请求处理链里等待 CLI；同时给后台资源设上限，防止 CPU/内存占满使 Web 卡顿。

概念数据包括 Agent、项目绑定、Conversation/Message、Assignment、Run、待决问题、
回传 outbox、带版本的项目检查点。已有个人 Task 是用户承诺，不应被另一套同名技术任务替代；
首轮 Assignment 记录执行委托，未来可引用个人 Task，不先双写两套状态。

建议会话、委派和 outbox 共享同一个事务拥有者/SQLite 数据库，以保证派工及回传原子提交。
personal store 虽已有 Source/Claim/Policy/Task 等实现及测试，但当前 main-web/main-chat
未实例化它。本轮继续不接入其自动认知/任务写入，不把“存在 store”当作“已有完整连接”。
保留该模块及测试，不假设它与聊天 store 各自 commit 就是一个原子事务。
产物文件不与 SQL 假装原子：先写临时文件、完成并校验，再登记引用；缺失/损坏须可诊断。

### 5.2 当前会话存储必须先解决的具体问题

当前 inbox 有 conversation_id，但 main_conversation_messages 没有会话字段，
readRecentContext/readContextThroughMessage 也没有按会话隔离。
foreground 的 main 是可由构造参数覆盖的默认值，并非不能配置的硬编码；仅更换该参数
依然无法解决上述消息隔离问题。多会话 UI 上线前必须完成存储和读取路径的迁移验收。
所以不能只在 UI 加一个群聊或多传一个 conversationId 就声称支持多会话。

建议迁移到统一、按 conversationId 隔离的消息存储；主聊天旧接口暂以 main 会话适配。
消息需分开记录真实作者（user / main-agent / work-project-agent / runtime）与模型 API role，
不能把系统派工事件伪装成用户说的话。消息与上下文按持久追加序号排序，时间仅作描述。

迁移先备份、版本化、事务执行；验证原消息 ID、原顺序、inbox 关联和登录可用。
仅在确认旧数据确为单主会话后回填 main；发现其他 conversationId 或无法解释的关联时
停止迁移，不把历史猜测归属到某个群。不长期保留两套互相竞争的 conversation DDL。
回退需匹配数据库版本及备份，不能让旧二进制盲读新 schema；新写入数据的保留需单独处理。

### 5.3 现有模块如何处理

| 现有部分 | 建议动作 |
| --- | --- |
| main/inbox、runtime、foreground | 保留耐久接收、锚点与单前台原则；增加会话隔离、受限委派和专用结果消费 |
| frontbrain/types、deepseek | 在原文本能力旁增加受校验工具协议；限制前台工具轮数，不变成长执行 loop |
| AgentCore | 复用已存在的工具循环与回合串行化，改造上下文、工具面、question、Run 四项持久边界 |
| AgentBackend、session readers | 复用 CLI 启动/续接以及增量读取的持久 offset、截断检测；补能力声明、隔离环境和宿主终态证据 |
| RunRegistry | 可作为活进程句柄缓存；SQLite Run 才是重启后真相，Promise 不能是唯一结果记录 |
| personal store | 已实现但未接入主聊天；本轮继续不接入自动认知/任务写入，不重写 Claim/Policy |
| main-web | 沿用登录和主聊天；增加领域会话入口、作者标识、派工/结果/问题卡及停止操作 |

页面刷新通过受鉴权的历史/状态快照恢复，SSE 仅用于增量通知。
所有会话和产物端点均检查登录和范围；输入内容按文本呈现，不能执行 CLI 输出的 HTML。
会话解析和工具层也已有部分 origin 标注，但其中部分依赖消息内容与已发送 prompt 的匹配。
这适合辅助展示，不是可信授权来源；不能借 origin 标签让 CLI 中的文本冒充用户新指令。

## 6. 怎样验收这轮交付

测试分为纯状态/假执行器测试、真实 CLI 隔离测试、真实浏览器流程。
前两项通过不能替代最后一项；真实模型回答好看也不能替代状态和权限证据。

| 案例 | 通过标准 |
| --- | --- |
| 明确委托 | 真正生成一个 assignment，群聊可见派工；接收失败不显示已派工 |
| 模糊或闲聊 | 未绑定项目/不清楚意图时先问；讨论未来工作不启动 CLI |
| 后台期间聊天 | 人为保持执行器未完成，主聊天仍能接收并完成另一轮模型回复；不只证明按钮能点 |
| 持久领域身份 | 服务重启、第二次跟进后沿用 agent/project；能依据已有证据回答，不只沿用昵称 |
| 上下文隔离 | 用合成主私聊秘密/其他项目事实测试，领域 context 和产物均不含无关内容 |
| 同项目第二委托 | 如实排队，无并发续写同一原生 session，无静默替换第一次目标 |
| 去重与提交故障 | 相同输入 ID、工具提交后的超时/重试，只产生一个委派和一条派工消息 |
| 群聊交互 | 补充/回答到正确领域；群聊回显不会被当新委托再次执行 |
| 来源伪造 | 模型/客户端伪造作者或 origin、结果中夹带新指令，不能创建新的授权执行 |
| 结果公平交付 | 连续注入用户消息，仍在定义的安全点调度界限内生成汇报；不改在途上下文 |
| 离线与重复回传 | 关闭浏览器仍持久交付；提交汇报后断线/重启只展示一份，delivered 不等同已读 |
| 事件边界 | 新 outbox 不消费/恢复旧 domain-update/timer；回传失败不启动第二前台循环 |
| 追问 | CLI/领域缺信息时结束运行并等待；主聊天或群聊任一回答只恢复一次 |
| 重启窗口 | 覆盖事务前后、启动前后、完成写盘前后、回传前后；未知不重跑，已存结果可补投 |
| 取消竞争 | 启动同时取消、取消后迟到结果、PID 失效均不谎报；旧回执不能覆盖新状态 |
| 模型/CLI 故障 | 超时、额度不足、无 session、结果解析失败均有真实状态；后台故障不锁住主聊 |
| 只读与隐私 | 用合成诱导内容尝试写项目、越界读、联网、执行脚本；真正被阻断而非模型自觉拒绝 |
| 证据质量 | 报告注明检查范围与版本；未执行测试就写未执行，不以退出码代替目标达成 |
| 原功能与迁移 | 登录、历史、多行输入、重试不丢草稿继续可用；旧记录未清空、未混入群聊 |

真实验收只用明确批准的项目与输入范围。记录运行标识、提交版本、断言和脱敏产物，
不把个人原始对话、密钥或真实隐私目录内容复制进测试 fixture 或 git。

## 7. 下一步：先验证会改变方案的两项能力

不再逐项重问第 0 节已收敛的方向。先准备两个小型技术预检，均使用合成输入和私有临时目录，
不迁移生产数据、不读取真实主人上下文、不操作真实工作项目：

1. **模型工具协议**：对当前配置的模型/客户端组合，验证非思考模式下工具选择、参数解析、
   tool call/result 配对与续接、拒绝无效参数、普通聊天不误触发、超时及恢复。
   工具仅做无副作用回执。记录脱敏协议产物、时延和用量，设置调用预算；一次成功不构成稳定性保证。
2. **执行权限**：使用合成文件和假秘密分别验证允许读取、禁止写、越界读、环境继承、
   插件配置和工具外联；包含新 session 与 resume。验证宿主程序能拒绝不满足要求的组合。
   若有效隔离需要额外 OS 配置/权限或改变 provider，报告具体缺口，请用户决定，不能自行放宽。

预检结果是接入可行性证据，不是完整交付。若模型协议不满足，带证据讨论结构化输出替代；
若 CLI 隔离不满足，讨论受控读取/更强隔离或缩小能力，不能静默切换执行器和隐私边界。

通过后顺序为：会话/状态/迁移规格 → 假执行器完整闭环及故障注入 →
受限真实 CLI 接线 → 明确批准的真实项目 + 浏览器端到端验收。
多会话存储迁移必须早于群聊正式上线，但不妨碍先做两个独立预检。

**仍需在接入前确定的事项：**具体项目与允许传给模型的内容、预检后选定的 backend、
其必要认证方式，以及故障恢复/上下文预算/公平调度的工程参数。前两类涉及用户授权，
工程参数通过规格与测试收敛，不要求用户逐字段审批。

本稿更新不授权运行生产委托、执行数据库迁移、部署或 push。
